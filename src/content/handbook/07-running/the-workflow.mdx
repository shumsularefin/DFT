<Why>

A single VASP run answers one question. A real project asks several in a fixed order: first find the structure, then compute the electrons on that structure, then ask what you want to know about them. If you change the order, or change a setting between steps that must stay the same, the numbers from later steps no longer belong to the structure you relaxed. The protocol below is the order one researcher uses <Cite id="S-042" />.

</Why>

<Intuition>

<Callout variant="note" title="This is the author's protocol">

The five quoted sentences below are the author's own notes, reproduced word for word, typos included. They are one working practice, not a rule of VASP. The notes after each one come from the Workflow Handbook's annotations and cite the VASP wiki where it agrees <Cite id="S-042" />.

</Callout>

<Callout variant="note" title="Follow it step by step">

The [Workflow](/workflow/) section turns this protocol, and every calculation after it, into a path you can follow: one page per step with the INCAR, the commands, the files to carry over and what to check before moving on.

</Callout>

**Step 1, Relaxation.** "Prepare four INPUT files and changes it as it requires. Run relaxation with encut of 1.3 of Enmax. Ediff, ISPIN, Magmom. INCAR can be prepared from VASPKIT."

Why: forces and stress are only meaningful at the structure you want. The 1.3 factor reduces Pulay stress when the cell changes, and `ISPIN` with one `MAGMOM` value per atom tells VASP the system is magnetic <Cite id="S-042" />.

**Step 2, SCF in the same folder.** "Same folder RUN SCF calculation. ISTART should be 1, INCAR will be generated from VASPkit. Try Converge repeatedly. For DOS, LORBIT = 11."

Why: `ISTART = 1` reads the `WAVECAR` the relaxation left in the same folder, so the run starts close to the answer. `LORBIT = 11` writes the projected DOS <Cite id="S-042" />.

**Step 3, Band structure.** "For BAND, Run SCF again without ICHARG=11 in INCAR, then generate KPATH.in which will be KPOINTS vaspkit 3 - 303. For data analyasis, vaspkit 21 211."

Why: a band path is not a uniform mesh, so a line-mode run cannot converge the density itself. The Workflow Handbook gives two routes: from VASP 6.3, one SCF with a uniform `KPOINTS` and the path in `KPOINTS_OPT`; or a second run on the path that reads the SCF `CHGCAR` with `ICHARG = 11` <Cite id="S-042" />.

**Step 4, Elastic properties.** "For elastic Properites, Prepare INCAR similar to Relaxation, but IBRION will be 6-8 and ENCUT=620. Comment out NCORE. vaspkit 2 - 203."

Why: `IBRION = 6` with `ISIF = 3` distorts the cell to get the elastic constants. It runs without band parallelisation, so `NCORE` can stop it <Cite id="S-042" />.

**Step 5, Optical properties.** "For Optical Properites, run SCF again up to -06 to -08 and then generate INCAR from vaspkit. After SCF calculate get the grep NBANDS OUTCAR. Then take NBANDS 3 times of it with closest ceiling numbers. Add ISPIN and magmom if requires. For data analysis, vaspkit 71 - 711."

Why: optics needs many empty bands, so the author triples `NBANDS` and rounds up to a number the core count divides. The tight `EDIFF` of 1E-6 to 1E-8 matches the wiki examples <Cite id="S-042" />.

</Intuition>

<TheMath>

<Level min="intermediate">

Each step is the same Kohn-Sham problem with different questions asked of it. What must be identical between linked steps is everything that defines the energy functional: `ENCUT`, `ISPIN`, `MAGMOM`, `LMAXMIX`, the functional, any `LDAU` tags, and the cell. What may change is what you ask for: `NSW`, `IBRION`, `LORBIT`, `NBANDS` and the k-points <Cite id="S-042" />.

</Level>

</TheMath>

<InVasp>

The relaxation, SCF and band INCARs from the handbook, with their changes. The band INCAR below is route B (a run on `KPATH.in` that reads the SCF charge density):

<VaspFileExplorer
  kind="INCAR"
  code={`ICHARG  = 11           # read the SCF CHGCAR and keep it fixed
PREC    = Accurate
ENCUT   = 520          # same as the SCF
EDIFF   = 1E-6
ISMEAR  = 0
SIGMA   = 0.05
LORBIT  = 11           # PROCAR for projected (fat) bands
ISPIN   = 2            # same spin settings as the SCF
MAGMOM  = 2*5.0 4*0.6
NSW     = 0
LWAVE   = .FALSE.
LCHARG  = .FALSE.`}
/>

Only the band run sets `ICHARG = 11`, and it inherits its physics from the `CHGCAR`, so `ENCUT`, `ISPIN` and `MAGMOM` match the SCF. These example files carry no `LMAXMIX`, which a d-element system normally needs. That is an open question about the handbook (Q-019), and this site's INCAR checker raises a warning for it.

The project folder from the Workflow Handbook, one folder per job type <Cite id="S-042" />:

<VaspFile
  name="shell"
  code={`Compound/
├── 00_conv/       encut_400 … encut_700/   kpt_0.05 … kpt_0.02/
├── 01_relax/      relax → cp CONTCAR POSCAR → SCF in the same folder (ISTART=1)
│                  → CHGCAR, WAVECAR, DOSCAR (DOS via LORBIT=11)
├── 04_band/       SCF without ICHARG=11 + KPATH.in (303) as the band path
├── 05_optics/     LOPTICS, NBANDS ≈ 3× default
├── 06_elastic/    IBRION=6, ISIF=3
├── 07_eos/        s_0.97 … s_1.03/
├── 08_phonon/     SPOSCAR, disp-001 …   (phonopy)
├── 09_dielectric/ LEPSILON, IBRION=8   → Born charges, ε∞, ε0
├── 10_bader/      LAECHG → AECCAR0, AECCAR2
├── 11_magnetic/   NM/ FM/ AFM1/ AFM2/   (same supercell)
└── 12_hse/        or 12_dftu/, 12_r2scan/`}
/>

<Callout variant="mistake" title="Back up the relaxation before the SCF">

The relaxation and the SCF share `01_relax/`, so the SCF overwrites the relaxation's `OUTCAR` and `CONTCAR`. Copy them first (for example to `OUTCAR.relax` and `CONTCAR.relax`) <Cite id="S-042" />. Why: the relaxation `OUTCAR` is the record of the forces, the stress and the final energy you report; without it you cannot show that the structure converged.

</Callout>

Every other calculation gets its own folder with copies of the files it needs <Cite id="S-042" />.

Between stages, copy `CONTCAR` to `POSCAR` and carry the files the next step reads (`WAVECAR`, `CHGCAR`) <Cite id="S-042" />. VASPkit does much of the file preparation. Its command map is in a later topic <Cite id="S-020" />.

</InVasp>

<WhatChanges>

| If you change...                        | ...between steps        | ...what goes wrong                              |
| --------------------------------------- | ----------------------- | ----------------------------------------------- |
| `ENCUT` after the relaxation            | The basis set           | The SCF no longer matches the relaxed structure |
| `MAGMOM` in the band run                | The magnetic state      | Bands that do not belong to the SCF density     |
| The order: bands before SCF             | No converged `CHGCAR`   | The `ICHARG = 11` run has nothing to read       |
| `EDIFF` from 1E-5 to 1E-8 before optics | Tighter electronic loop | More steps, cleaner dielectric function         |

Why this order: each step needs the result of the one before. Why these values: they carry the physics from step to step. What happens if you skip a step: you compute properties for a structure that is not the minimum.

</WhatChanges>

<Mistakes>

<Callout variant="mistake" title="Starting the SCF from the original POSCAR">

Copy `CONTCAR` to `POSCAR` first, or the SCF runs on the unrelaxed structure.

</Callout>

<Callout variant="mistake" title="Different settings in linked runs">

A changed `ENCUT`, `ISPIN` or `MAGMOM` between the SCF and the band run silently breaks the link <Cite id="S-042" />.

</Callout>

<Callout variant="mistake" title="Treating the protocol as the only way">

It is one researcher's practice. Convergence tests (module 8) come before any of it.

</Callout>

</Mistakes>
