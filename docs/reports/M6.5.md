# M6.5 Optional progress sync with Firebase (Spark)

Status: done        Branch: claude/m6-5-progress-sync        PR: see docs/PROGRESS.md (stacked on M7.4, PR #40)

Tier B (fast model), as the work order says. Dependencies M6.4 and M0.2 are done.

## What was built
- **`src/lib/sync/engine.ts`**: pure sync engine, no Firebase import. Merge on sign-in and on resume (cloud copy merged into the device copy with `mergeStates`, written back only if the cloud copy differs), at most one write per 60 s while the state changes, an immediate flush when the page is hidden or the browser comes back online, exponential backoff 30 s to 15 min, six statuses (off, signing in, syncing, synced at a time, offline, error). Safety rules: nothing is written before the cloud copy has been merged in; an unreadable cloud copy (newer format) is never overwritten; an empty state is never written automatically.
- **`src/lib/sync/firebase.ts`**: the only file that imports Firebase (`firebase/app`, `firebase/auth` Google popup, `firebase/firestore/lite`). Reached only through `import('./firebase')` in `controller.ts`.
- **`src/lib/sync/controller.ts`, `config.ts`**: config from `PUBLIC_FIREBASE_*` (all four or the feature is hidden, D-026), the store subscription, `visibilitychange` and `online` hooks, and a remembered "sync chosen" flag so a later visit resumes the session without a new popup.
- **`SyncPanel.tsx`** on `/progress/` (full panel: sign in, sign out, "Delete my synced data" with confirmation) and a one-line status on `/practice/`. Rendered only when the build has the config.
- **`firestore.rules`**: owner-only read, write and delete of `users/{uid}/state/main`; shape fixed to `{version == 1, learner (string, at most 900000 chars), updatedAt == request.time}`; every other path denied. `firebase.json` gained the `firestore` section (rules) and an emulator entry; no other service.
- **Rules tests** (`tests/rules/`, `npm run test:rules`) on the real Firestore emulator; new CI job `firestore-rules` (installs Java).
- Privacy page, practice "how this works" text and progress page text updated; `docs/SETUP_FIREBASE.md` section 6 lists what the author must switch on; source S-069 added; D-083; Q-049.
- Budget entry `lazy.firebase`: 80 KB gz, measured **56.1 KB** (one file). No page class grew (`/progress/` 107.2 KB and `/practice/` 111.7 KB of 200 KB).

## Quota arithmetic (Spark figures from Q-006, not confirmed from the pricing page)
Assumed limits per day for the whole project: 50,000 reads, 20,000 writes, 20,000 deletes, 1 GiB stored.

Worst case for one active user in a day:
- **Writes**: the engine writes at most once per 60 s, and only after a change. Eight hours of answering in every single minute is 480 writes. Add 50 page-hidden flushes and 100 resume writes (a resume writes only when the merge differs from the cloud copy) for a hard ceiling of about **630 writes**.
- **Reads**: one read per page load on `/practice/` or `/progress/` (resume) plus one per sign-in. 300 loads is **300 reads**.
- **Deletes**: one, only when the user presses "Delete my synced data".
- **Stored**: a state at the 200 events per concept cap for 80 concepts measured 832,031 characters in a test (under the 900,000 rule bound and the 1 MiB document limit); a light user (20 concepts, 20 events each) measured 21,711.

What that allows per day: the write limit binds first, 20,000 / 630 is about **31 users** if every one of them were at the absolute ceiling, but a realistic 30-minute practice session is at most about 35 writes (30 plus a few flushes), which is about **570 users a day** at the write limit. Reads allow 50,000 / 300 = 166 ceiling users or thousands of typical ones. Storage: 1 GiB / 832 KB is about 1,290 ceiling users, 1 GiB / 22 KB is about 48,000 light ones. A single constant (`WRITE_INTERVAL_MS`) raises the write interval if the project ever nears the limit. Authentication on Spark has its own limits, which were not checked (Q-049).
