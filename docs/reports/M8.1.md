## What was built
- `scripts/data/build_shannon.py` (pinned venv, pymatgen 2026.10.24): exports every entry of pymatgen's Shannon table to `src/data/shannon-radii.json`, one entry per line, sorted by Z, oxidation state, CN, geometry, spin. Coordination keys map to integers (`I` 1 ... `XIV` 14) with `SQ` and `PY` kept in `geometry`; `High Spin` / `Low Spin` / empty map to `HS` / `LS` / null. It aborts on any unknown key or a duplicate. `--date` fixes `_meta.generated`; with the same pymatgen and date the output is byte-identical, and Prettier leaves it unchanged.
- `_meta`: source S-001 via S-034, pymatgen version, generator, date, 492 entries, 94 elements, unit, `anomalies`, licence and completeness status pointing to Q-002. Size 48.8 KB raw, 4.4 KB gzip (the work order guessed about 25 KB; the explicit `null` fields required by the schema account for the difference). Imported only by `src/lib/perovskite/shannon.ts`; no page imports it yet.
- `src/lib/perovskite/shannon.ts`: `getRadius({ el, ox, cn, spin?, geometry?, kind })` returns `{ ok: true, value, entry, note? }` or `{ ok: false, reason, message, available }` with reason `unknown element`, `no entry`, `geometry required` or `spin required`. Rules:
  - no nearest coordination, no interpolation, no other oxidation state;
  - both HS and LS listed and no spin given: `spin required` with both entries;
  - only one spin listed (for example Cu3+ CN VI, LS only): that entry, with a note saying so; a spin that is not listed: `no entry`;
  - a spin given where the table does not distinguish spin: the value, with a note;
  - geometry omitted: the plain entry, with a note when SQ or PY also exists (Cu2+ IV and IVSQ); if only SQ or PY exists (Pb2+ IVPY): `geometry required`.
  - Helpers `oxidationStates`, `coordinations` (with geometry), `spins`, `coordinationLabel`, `ionLabel`.
- `scripts/data/compare_shannon_ic.py`: stdlib-only diff of the bundled file against a saved copy of the Imperial College database page (see Completeness).

## Completeness
The original paper could not be read: journals.iucr.org and doi.org returned 403. The Imperial College online Shannon database (http://abulafia.mt.ic.ac.uk/shannon/radius.php, all elements on one page; plain HTTP worked, HTTPS was reset) could be read. It states that all its data are taken from Shannon (1976). Result of `compare_shannon_ic.py` on the page saved 2026-11-18:

| | Bundled (pymatgen) | Imperial College |
|---|---|---|
| Rows | 492 | 497 |
| Species | 94 elements | 96 (94 elements plus D and OH) |
| Keys in common | 491 | 491 |
| Value differences on common keys | none (ionic and crystal, exact) | |
| Only here | Eu CN VII with no oxidation state | D+ CN II; OH- CN II, III, IV, VI; Eu3+ CN VII |

Per-element entry counts agree for all 94 elements (the Eu row is counted under Eu in both). D and OH are not elements, so pymatgen's per-element table has nowhere to put them; they are not added. The Eu row is the same row in both (ionic 1.01, crystal 1.15); the database gives it as Eu3+, pymatgen has an empty oxidation key. It is exported as `ox: null`, listed in `_meta.anomalies`, and never returned by the lookup (tested: Eu3+ CN 7 gives `no entry`). Assigning Eu3+ would change the Ln3+ coverage in the golden `perovskite_reference.json`, so it is left to the author (Q-002).

Limit of this check: the database is a transcription of S-001, and pymatgen may have been built from it, so agreement shows a faithful copy, not an independent reading of the paper. S-001 stays `cited-from-memory`; its notes record the check.
